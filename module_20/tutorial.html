Module 20 — Training Loops & Mini-Batches

Don't review all 10,000 case files before every decision

01 · The Big Analogy

Ada needs to improve her case-solving strategy. Full-batch GD says: "Read all 10,000 case files, compute the average lesson, update your strategy once." That takes all day for one update.

Mini-batch SGD says: "Grab 32 random case files. Read those. Update your strategy. Grab 32 more. Update again." Each update is noisier — 32 cases don't perfectly represent all 10,000 — but you get thousands of updates per day instead of one.

The noise isn't just a cost. It's also a benefit: the randomness helps Ada escape local habits (local minima) that full-batch review might reinforce.

02 · The Training Loop Anatomy

for epoch in range(EPOCHS):
    # shuffle the training data every epoch
    idx    = rng.permutation(len(X))
    X_shuf = X[idx]
    y_shuf = y[idx]

    batch_losses = []
    for start in range(0, len(X), BATCH_SIZE):
        X_batch = X_shuf[start : start + BATCH_SIZE]   # 32 samples
        y_batch = y_shuf[start : start + BATCH_SIZE]

        # forward → loss → backward → update
        probs = model.forward(X_batch)
        loss  = loss_fn(probs, y_batch)
        model.backward(probs, y_batch)
        model.update_weights()
        batch_losses.append(loss)

    epoch_loss = np.mean(batch_losses)   # average over all batches

    # validation — no weight update, just measure
    val_probs = model.forward(X_val)
    val_loss  = loss_fn(val_probs, y_val)

03 · Three-Way Data Split

SplitPurposeUsed for weight updates?
TrainingModel learns from this dataYes
ValidationTune hyperparameters, detect overfittingNo — measure only
TestFinal unbiased performance estimateNo — look once at the end
Never use test loss to decide when to stop training. That would make the test set part of the training process and inflate your reported accuracy. The validation set is the correct early-stopping signal. The test set is untouched until you're done.

04 · Batch Size Trade-offs

Batch sizeGradient qualityMemory useTypical use
1 (online SGD)Very noisyTinyRarely used in DL
32–128Good balanceModerateDefault for most tasks
512–4096More accurate gradientHigh (needs GPU)Large-scale training
All samplesExact gradientFull dataset in RAMOnly feasible for tiny datasets
Rule of thumb: Start with batch_size=32. If training is slow, double it. If the model doesn't converge, halve it. Scale learning rate proportionally (linear scaling rule: lr = base_lr × batch_size / 32).

06 · Brain Exercise

Look at the step_loss.png plot — the per-batch losses zigzag wildly compared to the smooth epoch-level curve. Is that noise a problem or a feature?

And: if you kept halving the batch size (32 → 16 → 8 → 1), what would happen to the loss curve and to training time?

Noise as feature: The noise helps escape sharp local minima — a sharp minimum has high curvature, so a noisy step can hop over it to a flatter (and often more generalisable) minimum. This is one reason SGD often outperforms full-batch GD on generalisation, even if it has a higher final training loss.

Smaller batches: The loss curve becomes increasingly jagged. Training time per epoch may decrease (fewer RAM operations) or increase (Python loop overhead dominates). At batch_size=1 the gradient is maximally noisy and the network may never converge — you'd need a much lower learning rate.

07 · Q&A

Q: What is an "epoch" vs a "step"?
An epoch is one complete pass through the training data. A step (or iteration) is one weight update using one mini-batch. If you have 1000 samples and batch_size=32, each epoch has ceil(1000/32) = 32 steps. After 10 epochs you've completed 320 steps.
Q: Why shuffle the data every epoch?
Without shuffling, the model sees the same batch order every epoch. If the data is sorted (e.g., all solved cases first), each epoch's gradients are systematically biased — early batches push weights one way, late batches push them another. Shuffling ensures each batch is a random sample from the full distribution.
Q: What is early stopping?
Monitor validation loss during training. When val_loss stops improving (or starts rising), stop training — the model is beginning to overfit. In practice, you wait a few epochs to confirm the trend isn't a fluctuation, then restore the weights from the epoch with the best val_loss. PyTorch-Lightning and Keras have built-in EarlyStopping callbacks for this.
