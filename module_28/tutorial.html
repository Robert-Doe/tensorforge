01 · The Big Analogy — Everything Together

Ada's agency has grown. She now receives dozens of new cases a day. She can't personally train every new detective on how to fill in the case form, normalize the evidence scores, or convert district names to numbers. She needs a system — one that takes a raw case report (with missing fields, text district names, and mixed data types) and automatically produces a verdict.

That system is an ML Pipeline. It's Ada's entire operation codified: the intake clerk (imputation), the file clerk (feature engineering and scaling), the junior detectives (the trained model), and the verdict stamp (predict). When a new case arrives, it enters one end of the system and a "SOLVED" or "UNSOLVED" prediction exits the other — with no manual preprocessing by the caller.

And because the system is saved to disk, next year's Ada can pick it up without re-training anything. This is what makes ML useful in production rather than just in notebooks.

02 · The Eight Steps

1
Data Loading & Inspection
Load CSV, count missing values, check class balance. Never touch test data here.
2
Missing Value Imputation
Fill NaN with column medians. Medians are robust to outliers; means are not.
3
Train / Test Split
Split FIRST. Everything after this point must see only training data. Test set is locked away until Step 6.
4
Model Selection (CV)
Compare 3 algorithms with stratified k-fold CV. Rank by AUC. No test data used.
5
Hyperparameter Tuning
Grid-search the CV winner. Still no test data. Best params chosen by cross-validation score.
6
Final Evaluation
Fit on full training set. Evaluate ONCE on held-out test. This is your honest accuracy estimate.
7
Save Pipeline
Serialise the fitted Pipeline (preprocessor + model). The whole inference graph, not just weights.
8
Inference on New Data
Load the saved pipeline. Pass raw rows (same format as training). Call predict(). Done.

03 · The Critical Rule — Test Set Isolation

# WRONG — classic data leakage:
scaler.fit(X_all)           # sees test data during fit!
X_scaled = scaler.transform(X_all)
X_train, X_test = train_test_split(X_scaled, ...)

# CORRECT — split first, then fit only on train:
X_train_raw, X_test_raw, y_train, y_test = train_test_split(X, y, ...)

pipeline = Pipeline([
    ("scaler", StandardScaler()),    # fit() called only on X_train inside CV
    ("model",  RandomForestClassifier()),
])
pipeline.fit(X_train_raw, y_train)   # scaler.fit happens here — never sees X_test
pipeline.score(X_test_raw, y_test)   # scaler.transform(X_test) uses train stats only
Why does leakage matter? If the scaler's mean and std were computed on the full dataset (including test rows), the test-set evaluation is optimistic — the model has indirectly "seen" the test distribution. The reported accuracy looks better than what you'd get on truly new data. This is one of the most common bugs in ML projects and is hard to detect without code review.

04 · Save and Load the Full Pipeline

import pickle

# Save — the whole Pipeline (preprocessor + tuned model), fitted on training data
with open("saved_models/best_pipeline.pkl", "wb") as f:
    pickle.dump(fitted_pipeline, f)

# Load — months later, on a different machine
with open("saved_models/best_pipeline.pkl", "rb") as f:
    loaded = pickle.load(f)

# Inference — raw data, same format as training
new_case = pd.DataFrame({
    "district":          ["North"],
    "case_type":         ["Theft"],
    "num_witnesses":     [5],
    "evidence_strength": [0.92],
    "suspect_age":       [34],
    "days_open":         [7],
    "prior_convictions": [2],
    "tip_received":      [1],
})
prediction = loaded.predict(new_case)      # ["SOLVED"] or [1]
proba      = loaded.predict_proba(new_case)[:, 1]   # [0.93]
Pickle vs joblib vs ONNX: Pickle works but is tied to the Python version and scikit-learn version that saved the model. For production, use joblib.dump() (faster for large numpy arrays) or export to ONNX format for cross-language inference. For deployment, Docker containers pinning the exact library versions are the robust solution.

07 · Brain Exercise

The pipeline saves all preprocessing fitted on the training data. If, six months later, a new district "Central" appears in production data that was never in the training set, what happens when you call loaded.predict(new_case)?

Specifically: what does OneHotEncoder(handle_unknown="ignore") do with "Central"? Does the model crash? Is the prediction reliable?

Answer: The pipeline does NOT crash. handle_unknown="ignore" means unseen categories are encoded as all-zeros — as if the district column were absent. The model receives a valid input and produces a prediction, but that prediction may be unreliable because the model never saw this district during training. This is called distribution shift: the production distribution has drifted from the training distribution. The solution is to monitor prediction confidence on new data, set up alerts when unseen categories appear, and periodically retrain on fresh data. Trusting a silently-degraded prediction is a real production risk.

08 · Q&A

Q: Why evaluate ONCE on the test set instead of checking it repeatedly?
Every time you look at the test set to decide what to change next, you're effectively training on it. After 10 such peeks, your model has been implicitly tuned to the test set's specific noise and quirks — it won't generalise to new data nearly as well as the reported accuracy suggests. The test set is your single, final, honest performance estimate. Cross-validation is the correct tool for all intermediate decisions.
Q: What should I do if the CV accuracy and test accuracy are very different?
A big gap usually means one of: (1) the test set is small and the estimate is noisy — compute a confidence interval; (2) you peeked at the test set during development (leakage); (3) the train/test split is not representative — try stratified splits or check for time-based splits if the data is temporal; (4) the test set has different class balance or feature distribution than training — investigate with a data audit.
